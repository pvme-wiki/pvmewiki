PvME Wiki

A MediaWiki site that hosts PvME's RuneScape 3 bossing guides as editable, attributed pages. It is one Docker image and one PostgreSQL database: the image is replaceable, and the database is the only copy of everything people do on the wiki.

What the design holds to

The database is the asset; the image is replaceable.

PostgreSQL holds the only copy of community edits, accounts and moderation state. A redeploy never undoes anything in it; only a backup does.

Startup refuses instead of repairing.

Two of seven database states start the wiki. Every other state stops the container with one line on stderr, because a wrong guess could destroy edits that exist nowhere else.

No runtime script overwrites a changed page.

Packaged guides are written only onto pages still at their recorded baseline; the picture guide only onto missing pages.

Guide text is verbatim; presentation is additive.

The reader adds around the saved article and never rewrites it (root AGENTS.md).

The exporter fails closed.

It throws on anything it cannot reproduce exactly, and Copy to wiki copies nothing while any media lacks a verified route.

Everything here lives in wiki-host/. The other top-level directories belong to an earlier reader prototype and are not built, tested or deployed; the one link is that wiki-host/tools/build-corpus.mjs reads guide snapshots from editor/content/.

Container startup

wiki-host/runtime/start.sh runs three PHP steps, then Apache. It uses set -eu, so any step that exits non-zero stops the container before it serves a request. Each step logs one line per decision to stdout and failures as one line on stderr, never a URL, password or raw database error.

STEP 1

bootstrap.php

Validates config and the seed corpus, connects with TLS, takes a lock, decides what to do with the database. Installs and imports only into an empty database.

DBadvisory lock
STEP 2

install-visual-guides.php

Creates the picture guide and its four templates only where the page does not exist.

DBown lockedit --createonly
STEP 3

install-main-guides.php

Publishes each packaged page only if nobody changed it since its recorded baseline.

DBno lock; compare-and-swap
THEN

exec apache2-foreground

Serves requests on port 80. Its environment has no MW_BOOTSTRAP, so web edits stay moderated.

Why startup refuses instead of repairing

The marker says installing for the whole install. If any step fails, the next start sees IncompleteOrMismatched and stops: it does not retry the import, drop tables or run the installer again.

A database that is not empty and not marked could be another application's database or a partly restored backup. A database marked for a different corpus digest may hold years of edits on top of an older seed. Any automatic repair would have to guess, and a wrong guess destroys community edits that exist nowhere else. Stopping costs an outage; guessing can cost the data.

For the same reason UseExisting does not run MediaWiki's update.php. A base image upgrade that needs schema changes is run by hand after a backup.

Fresh install, step by step (installFresh())
  1. Create the marker table with one installing row.
  2. Run MediaWiki's install maintenance script. The admin and database passwords are passed in mode 0600 files in a private temporary directory, never in argv. The installer's own LocalSettings.php is discarded.
  3. Copy the packaged LocalSettings.php into place (RuntimeSettings::activate, an atomic rename that replaces a symlink rather than following it).
  4. Run update --quick, delete the installer's sample Main_Page (only while it is the sole mainspace page with one revision), and importDump the seed XML.
  5. Check that the mainspace titles are exactly the seed titles, set MediaWiki:Mainpage to PvME, and mark the row ready.

The admin account is named Admin.

Health endpoint

/healthz.php (wiki-host/runtime/health.php) answers 200 ready only when all of these hold; otherwise 503 not ready, without saying why. It sends Cache-Control: no-store.

  • the settings paths and MW_SERVER are valid
  • the active LocalSettings.php is a regular file identical to the packaged one
  • the marker row for the packaged XML digest is ready
  • there are at least 381 mainspace pages

It counts pages; it does not check whether packaged guides were published or preserved.

Moderation during startup

New user edits go through the Moderation extension. The runtime scripts set MW_BOOTSTRAP=1 in their own environment (RuntimeConfig::bypassModerationInMaintenance) so the maintenance processes they start can save without the review queue. LocalSettings.php sets $wgModerationEnable = !RuntimeConfig::moderationBypassed(). Apache is started by start.sh, whose environment does not have the variable, so web edits stay moderated. Never set MW_BOOTSTRAP on the service.

Deploy and recover

Deploys on Render are started by hand. A redeploy replaces code, settings and packaged files; it never undoes anything in the database. Only a tested backup can do that.

Before a deploy

  1. On a clean checkout of the commit, run every check in Tests: npm test, the PHP tests, the corpus verifiers.
  2. Build the image locally and boot it against a throwaway TLS PostgreSQL. Expect ready from /healthz.php.
  3. If the release changes corpus/, production will refuse to start (IncompleteOrMismatched). Do not deploy it without a written migration plan.
  4. If the release changes the MediaWiki base image, plan to run update.php by hand; startup never runs it on an existing database.
  5. Take and test-restore a backup when the release touches anything that writes to the database: a base image change, new packaged pages, manual recovery.
  6. Start a manual deploy of the commit.

Rollback and backups

Redeploying an earlier commit replaces

  • code and settings
  • packaged files in the image

It does not undo

  • pages a newer image published; the runtime never deletes or reverts a page
  • any edit, account or moderation state
  • and an earlier image with a different seed corpus is refused at startup

Back up before every change that can write to the database, and test that the backup restores. Use PostgreSQL client tools of the server's major version or newer.

pg_dump --format=custom --no-owner --dbname="$MW_DATABASE_URL" --file=pvmewiki.dump
# restore into a new, empty database, never over the live one:
pg_restore --no-owner --dbname="$RESTORE_URL" pvmewiki.dump

A restore is proven when the image boots against the restored database, logs PvME wiki ready: existing verified corpus and /healthz.php answers ready. Keep dumps outside the repository; they contain account data. The seed corpus in Git recreates an empty wiki with the imported guides; it cannot restore anything people did afterwards.

Why the release id is in the load path

LocalSettings.php sets $wgLoadScript to /load-<id>.php, where <id> is 16 hex digits of a hash over every .js, .json and .css file in the extension's modules/ directory (wiki-host/runtime/lib/PresentationRelease.php). wiki-host/runtime/wiki.conf rewrites that path to load.php.

Browsers cache ResourceLoader's startup response under its URL; with an unversioned load.php a reader could keep the previous release's module list. A query parameter does not work because ResourceLoader appends its own query string. A path changes with every release and stays cacheable between releases.

TLS modes

The runtime refuses unencrypted connections. Which mode applies depends on three facts:

verify-full default

Every connection verifies the server certificate against /etc/ssl/certs/ca-certificates.crt (RuntimePaths::CA_BUNDLE).

require

Encrypted, without certificate verification, for Render's internal network. Only when all three hold: MW_ALLOW_RENDER_PRIVATE_TLS=true, RENDER=true, and the database host matches RENDER_PRIVATE_HOST in RuntimeConfig.php.

refused

MW_ALLOW_RENDER_PRIVATE_TLS=true with any other host stops startup with Private TLS is limited to a Render private database host.

The runtime's own connections pass the mode explicitly and then check pg_stat_ssl. MediaWiki's database layer maps its setting only to require, so LocalSettings.php and the installer get the mode through PGSSLMODE and PGSSLROOTCERT (DatabaseConfig::exportTlsEnvironment).

Reader

Browser code that adds navigation, attribution and the Copy to wiki button around a guide. It never changes the saved article: everything it inserts sits outside .mw-parser-output, so it is never part of a revision and never reaches an editor.

When it runs, and when it does nothing

Loaded by the server

GuidePageDisplay (on BeforePageDisplay) loads the module only on the view action of a main-namespace page titled PvME or PvME/....

enhancePage() returns early when

  • VisualEditor is open or opening (.ve-active, .ve-activating)
  • the page has no entry in modules/navigation.json
  • there is no .mw-parser-output, or the toolbar already exists

A new page gets no navigation, heading or Copy to wiki until navigation.json is rebuilt and a new image deployed. The registry is a static file (limitation 12).

What it changes

Page heading

Compiled guides store their heading as <h1 class="pvme-source-title"> inside the article. The stylesheet hides it in read view and native-title.js copies its child nodes into #firstHeading. A MutationObserver repeats the copy after a VisualEditor save. The server sets the same heading first, so the page is right before the script runs; the browser tab title is unchanged.

Seed index pages

Pages still in the seed format (no nativeLayout) gain CSS classes, title attributes and ARIA labels only. Text, links and element order are untouched.

Boss landing pages

A landing page (registry entry with overview) transcludes the boss's overview guide with {{:...}}. The edit and history links and Copy to wiki point at that overview guide, because that is the text on screen (pageActions in toolbar.js, findPage in page.js).

Copy to wiki

One click reads the guide's latest saved revision from this wiki, converts it in the browser and puts RuneScape Wiki wikitext on the clipboard. Nothing is saved on either wiki and nothing is sent anywhere else.

Why the clipboard write starts before the fetch finishesBrowsers allow a clipboard write only while handling the click. Fetching the revision and loading the exporter takes longer than that window. So the handler starts navigator.clipboard.write() immediately with a ClipboardItem whose content is a promise, which resolves when the export is ready (writeToClipboardWhenReady in wiki-host/presentation/module/modules/reader/copy-to-wiki.js).

Exporter

exportRevision(revision, mediaCatalogue) turns one saved revision into wikitext that renders the same guide on RuneScape Wiki. It may restyle guide text but never drop, reorder or reword it, so whenever it cannot be sure the output carries the whole guide, it throws.

Media routes: how each image, video and embed reaches RuneScape Wiki

Approved image hosts

The catalogue's externalImagePolicies, plus one built-in policy: PNG files under https://img.pvme.io/images/, with no query string.

What "verified" means

isVerified counts an entry or host policy only when verified === true and its verification has a non-empty method, a parseable checkedAt date and an evidenceUrl on https://runescape.wiki/. It checks that the record is well formed, not that the evidence is still true.

Unresolved reasons, exactly: Destination mapping has not been verified. (an entry exists), No verified inline-image route or wiki File mapping. (image), No verified destination video/embed mapping. (video or embed).

What else the exporter copies or filters
  • Author-set style attributes are filtered to a short list of properties, and any value containing url(, expression(, var(, < or > is dropped (copiedStyle in render-guide.js).
  • Only a fixed set of attributes is copied.
  • The attribution block this wiki adds (div.pvme-source-attribution) is left out, because the export writes its own Source section.
  • The output contains one template call of its own: the contents box uses RuneScape Wiki's {{ToC}} (TABLE_OF_CONTENTS in render-guide.js).
  • Bare text outside <nowiki> loses its newlines (limitation 3). No packaged guide is affected.

Content pipeline

Content reaches the image as files committed to Git. Node scripts produce those files by hand on a developer machine; nothing is generated at build or run time. Each script's header comment is its full contract.

The content ruleFrom the root AGENTS.md: guide content is verbatim source material. Every source word, its order, gear note, rotation, caption, warning, link and visual must survive unchanged. Formatting, navigation and source-backed visual grouping may be added; guide text may not be rewritten, summarised, substituted, omitted or reordered. The audits exist to check exactly that.

How guide text is protected during compilation

wiki-host/tools/source-wikitext.mjs XML-escapes text nodes and wraps them in <nowiki>, so MediaWiki never reinterprets guide prose; the one exception is text inside the guide's own h1 title, which is escaped only. Media become <pvme-image>, <pvme-video> and <pvme-embed> tags. Preset previews are marked kind="addition" so they can never be mistaken for, or replace, source media.

Step 4 repairs two captured guides whose authors wrote literal placeholders such as <Boss> (<Style>); an HTML parser reads <Style> as a stylesheet and swallows the rest of the guide. It escapes each placeholder only where its exact context appears in both the capture and the authored file at the pinned revision. Run it again whenever step 2 fetched either page.

The registry and catalogue are staticnavigation.json, native-headings.json, source-media-hosts.json and the media catalogue are committed files. The running wiki does not update them when someone creates, moves or deletes a page. Content also cannot be rebuilt offline from Git alone: the capture, the media maps and the audits all read live sites (limitations 12 and 15).

Known limitations

What is imperfect, each with the code where you can confirm it. None is hidden by the tests; where a test pins the behaviour, the item says so.

1

A media tag without src gets the URL parser's raw message

media-markup.js calls requireWebUrl(attributes.src || ''), and new URL('') throws Invalid URL. The person sees the generic failure (item 4); a developer sees a message that does not name the tag.

Exporterpinned as a known defectwiki-host/tests/export-refusals.test.mjs
2

An unsafe link href is refused as "Unsupported media URL."

Links and media share requireWebUrl in media-routes.js, so a javascript: link is reported as a media problem.

Exporterpinnedwiki-host/tests/export-refusals.test.mjs
3

Bare text outside <nowiki> loses its newlines

toTextNode in published-markup.js drops every newline outside protected spans. A community edit that types plain text over two lines exports with the words joined. No packaged guide is affected: the compiler wraps all guide text in <nowiki>.

Exporterwiki-host/presentation/module/modules/export/published-markup.js
4

Copy to wiki shows one generic message for every refusal

Only unresolved media gets its own message. Every other error, including a template or an unbalanced tag, becomes "Couldn’t load this guide. Try Copy to wiki again.", which suggests a retry that cannot help.

Exporterwiki-host/presentation/module/modules/reader/copy-to-wiki.js
5

A linked video's poster image is dropped

write() returns early for linked-video and unresolved routes, before the code that emits the poster.

Exporterwiki-host/presentation/module/modules/export/media-markup.js
6

Boss landing pages are not exportable themselves

A landing transcludes its overview with {{:...}}, which the exporter refuses. Copy to wiki on a landing exports the overview guide instead (findPage in reader/page.js).

Exporterrefusal pinned for every landingwiki-host/tests/export-corpus.test.mjs
7

"Verified" means a well-formed record, not a re-check

The exporter cannot confirm that a catalogue entry's evidence is still true on RuneScape Wiki; a file renamed or deleted there breaks the export silently.

Exporterwiki-host/presentation/module/modules/export/media-routes.js
8

Clipboard writing has not been checked on a physical iPhone

The promise-based ClipboardItem path is tested only against jsdom stand-ins. The manual-copy text area is the fallback.

Readerwiki-host/tests/support/browser.mjs
9

The freshness badge depends on another site

Every guide view requests https://pvme.sanji3.dev/data/guide-history.json from the reader's browser, cached 15 minutes per tab. When that site is down the badge says the date is unverified. The wiki does not produce the feed.

Readerwiki-host/presentation/module/modules/reader/source-freshness.js
10

native-headings.json is read on every page view

GuidePageDisplay is built by newFromModuleFiles(), which reads and decodes the file on every request that runs BeforePageDisplay, including pages outside PvME/.

Readerwiki-host/presentation/module/includes/
11

navigation.json ships data the browser does not use

Its wikiTitles map is read only by media-catalogue/corpus-native-build.mjs, but the whole file is part of the reader module.

Readerwiki-host/presentation/module/modules/navigation.json
12

The navigation registry and media catalogue are static

A page created, moved or deleted on the wiki gets no navigation, heading or Copy to wiki until the scripts are rerun and a new image is deployed.

Data and contentwiki-host/tools/build-main-corpus.mjs
13

A fresh database does not reproduce production

Packaged pages are published only onto pages still at their recorded baseline, and those baselines are production text. On a fresh install the compiled guides are preserved as seed text. Only a database backup reproduces production.

Data and contentwiki-host/runtime/install-main-guides.php
14

On a fresh install the picture guide is replaced at once

Step 2 creates PvME/Amascut/Picture guide; step 3 replaces it with the redirect to the Amascut overview, because the new page matches the redirect's baseline. The picture guide stays in the page history, and the four templates remain.

Data and contentwiki-host/main-guides/amascut-picture-redirect.wiki
15

Content cannot be rebuilt offline from Git alone

The capture is of the live pvme.io site, the media maps query RuneScape Wiki, and the audits and baselines read the production wiki. The seed build reads editor/content/, and build-render-exceptions.mjs needs a pvme-guides clone two directories above the repository root.

Data and contentwiki-host/current-source/build-render-exceptions.mjs
16

install-visual-guides.php validates entries inside its publish loop

An entry with a bad file name or namespace stops the script only when the loop reaches it, so pages for earlier entries may already be published.

Runtimewiki-host/runtime/install-visual-guides.php
17

Any failed publication stops the container

A refused save calls fatalError, and start.sh runs with set -e. The script takes no advisory lock and relies on compare-and-swap, so of two containers starting at once, the one that loses a save race fails to start.

Runtimewiki-host/runtime/install-main-guides.php
18

Existing databases are never upgraded

UseExisting does not run update.php. A MediaWiki version bump that needs schema changes must be applied by hand.

Runtimewiki-host/runtime/bootstrap.php
19

MW_BOOTSTRAP must never be set on the service

LocalSettings.php disables Moderation whenever it is 1, in any process. Only the runtime's own maintenance processes should see it.

Runtimewiki-host/LocalSettings.php
20

The health check counts pages; it does not check packaged content

health.php requires at least 381 mainspace pages and a ready marker. It says nothing about whether packaged guides were published or preserved.

Runtimewiki-host/runtime/health.php
21

The prototype directories at the repository root are unmaintained here

editor/, server/, scripts/, src/, api/, reader/, content/, imported/ and docs/ belong to an earlier reader prototype. They are not built, tested or deployed, and their docs describe that prototype. The seed build still reads editor/content/.
